## Architecture

- **D26. Two layers of analysis: a universal shallow layer and per-language deep layers.** David's call, 2026-09-19, answering "isn't the logic similar for any code? I want it to work anywhere."
  - The **shallow layer** runs on any repository at all: file tree, imports read as text, dependency manifests across ecosystems, route conventions where they are detectable. Everything it produces is `inferred`. Its job is that the product never tells anyone their repository is unsupported.
  - The **deep layer** is one analyzer per language, and it is the only thing that produces `certain` edges, because resolving a call to its definition is irreducibly language-specific — the TypeScript compiler for TS/JS, an entirely different machine for Python, Java, Go or Rust.
  - Why this split rather than "universal everywhere": the headline promise, "changing this affects these four places", is only worth anything when the edge is `certain`. A map built only from inferred edges is a screen of dotted lines, and the honest answer it gives to "will this break something?" is "probably, we are not sure" — which is not an answer. Section 3 forbids us from claiming more, so shipping shallow-only would mean shipping a product that runs everywhere and answers nothing.
  - Everything above the analyzer is already language-agnostic and was built that way deliberately: the graph model, stable ids, re-analysis rules, the map, Q&A, and the prompt builder. Adding a language is writing one analyzer, not rebuilding the product (D7).
  - **Closed, 2026-09-19, by research: there is no such thing.** The one project that promised both language-agnostic resolution and no dependency install was GitHub's `stack-graphs`, and **GitHub archived it on 2025-09-09** (API reports `archived=true`; its final commit is the archive PR; the crate is frozen at 0.14.1 from 2024-12-13). It only ever covered four languages. Nothing replaced it. Every other route is either one indexer per language or requires a working build, which we refuse to run.
  - And the split is language semantics, not a tooling gap that someone will close. TypeScript and pyright are error-tolerant front ends: they resolve intra-project imports from source alone and mark the rest unknown. Go, Rust, Java and C++ type checkers need the resolved types of every import, so with no dependencies installed they produce **nothing**, not degraded output. Hold anyone who claims otherwise to this.
  - **SCIP is alive and is the right post-MVP shape, but not now.** It moved to independent governance on 2026-03-25 and there is now an official Node reader (`@scip-code/scip`, published 2026-09-03) — neither was true when the brief was written. The blocker is that SCIP has no call role and no JSX concept: its roles are Definition/Import/WriteAccess/ReadAccess/Generated/Test/ForwardDefinition. Reference-derived edges conflate a call, a type annotation, a re-export and reading a constant, so writing them into `calls` as `certain` would be a stronger claim than SCIP itself makes — the exact dishonesty D25 put a Postgres enum around. And `renders`, the demo's best moment, has no SCIP representation at all. Post-MVP it becomes a third analyzer behind the D7 seam, emitting `contains`/`imports`/`uses_package` as `certain` and references as `inferred`.
  - **D26 CORRECTION: the shallow layer is not all-inferred.** As originally written this undersold the fallback. A `contains` edge never crosses a file boundary — `def charge_card` at lines 40-58 of `billing.py` *is* a function of that name at those lines, which is a direct read. Likewise `<script src="./app.js">` and `<link href="./style.css">`, which the browser resolves by a fully specified rule with no configuration, and `uses_package` when a bare specifier appears verbatim in the manifest. Those are `certain`. What is `inferred` is everything that crosses a file boundary **by name** — `calls`, `renders`, `fetches` — and relative imports in languages whose resolution depends on configuration we do not have. The practical consequence matters: in a fallback repo the boxes and their contents are solid and only the lines between them are dotted, which is a materially different product from a screen of dotted lines.
  - **Shallow-layer scope for the MVP is half a day**: file tree, dependency manifests across ecosystems, literal-path imports, and a project kind that routes here instead of erroring. Tree-sitter symbol extraction (`web-tree-sitter`, no toolchain needed) is the right way to add real symbols to this layer later — a Step 5-or-later item, not Step 2.
  - **Language priority, evidenced: TS/JS alone covers roughly 85-90% of the repos this product will ever be pointed at.** Every mainstream AI app builder except Replit emits React plus TypeScript, and GitHub's Octoverse put TypeScript at number one in 2025 attributing it explicitly to AI-assisted coding. Order: TS/JS deep (in flight), static HTML/CSS/JS deep (D6), universal shallow for everything else, then Python — and Python is cheap when it comes, because pyright is itself a Node program and costs no extra runtime on the image.
  - **A larger completeness threat than language coverage**, worth its own look before widening anything: for Lovable and Base44 users, much of the app is not in the repository at all — the backend is Supabase or Lovable Cloud configuration and SQL, and Base44 runs on a proprietary runtime. We could support every language on earth and still show those users an incomplete map.

- **D27. `NodeRef` carries an optional `container`.** Found by the same research, in code written an hour earlier. The ref was `{type, filePath, name}`, so a file declaring `render()` on three classes hashed to **one** node and every edge that should have pointed at one of the three merged onto whichever was written last — silently, with no error, telling the user something false about their own code. The container is the enclosing symbol's name, deliberately not a line number or an index, because both churn when unrelated code moves and rule 1 of section 6.1 requires an id that survives edits elsewhere in the file.

## From the stack audit, 2026-09-18 (25 agents, verified against current docs)

These are corrections to how the brief says to build things. Each one was found by
reading current documentation, and the high-severity ones were re-checked by a second
agent trying to refute them. Full run: 53 findings, 8 high, 1 refuted.

- **D15. Pass 1 must read `tsconfig.json`/`jsconfig.json` for `baseUrl` and `paths` only — never the rest of the config.** The brief (6.2) says to build the ts-morph project without the repo's tsconfig. Taken literally that is a silent failure: `@/components/Button` is a bare specifier, so TypeScript walks `node_modules`, which does not exist in an unbuilt tarball, and resolves to nothing. Every alias import in an idiomatic Next.js app would produce no edge at all, and Pass 1 would emit a confident, disconnected graph. Keep the brief's intent (the repo's `target`/`lib`/`strict` never decide our parse) but lift the path mappings out, tolerating comments and trailing commas, and fall back to probing `@/* → src/*` then `./*`.
- **D16. Starting a run and streaming it are two endpoints, not one.** `POST /api/projects/:id/analyze` starts the run and returns an `analysis_run` id immediately; `GET .../runs/:runId/events` tails *persisted* events by cursor (`Last-Event-ID`) and closes on `run.completed`. The brief's sequence diagram runs the pipeline inside the SSE request, which cannot satisfy Step 3's "refresh mid-run without losing state" — a refresh opens a second, isolated request with no access to the first run's emitter. This keeps 6.2's "the pipeline knows nothing about HTTP" intact and is the same shape a background worker would need.
- **D17. Railway's real limits, since D3 picked it: 15 minutes maximum per HTTP request, closed after 5 minutes with no data transferred, websockets exempt.** So SSE must send a heartbeat every ~20s unconditionally — including across the long Pass 2 LLM call — and the route must set `Cache-Control: no-cache, no-transform` and `X-Accel-Buffering: no`. (For contrast, Vercel is 300s hard on Hobby and 800s max on Pro, which is what D3 avoided.)
- **D18. Strip the tarball's top-level directory at ingest.** GitHub archives extract to `{owner}-{repo}-{sha}/`, so the commit SHA would land inside every `file_path` and stable ids would change on every commit — breaking rule 1 of section 6.1 exactly where it matters. Store paths repo-relative and POSIX-separated, and assert in the Step 2 tests that no stored path contains the repo name or a SHA.
- **D19. `chat_messages` stores user turns, final assistant text, and citation node ids — never tool results or source snippets.** The obvious chat implementation persists tool output so the conversation survives a refresh, but `read_source` output *is* the user's source code, which would put it in Postgres and break the section 3 trust promise in the first feature that touches it. Re-fetch on render instead.
- **D20. Re-analysis stages rows under the new `analysis_run_id` and promotes atomically at the end.** The brief says re-analysis "replaces" static and llm rows, which read literally means mutating the live graph while the user is looking at it, and a run that fails halfway leaves a half-graph. Staging means a failed run drops its rows and the previous graph stands.
- **D21. `next/dynamic` with `ssr: false` is illegal in a Server Component.** Pages are Server Components by default, so the brief's graph-rendering note compiles only behind a thin `'use client'` wrapper module per graph. Ten-minute fix, an hour of confusion if undiscovered — and it lands on both of the most visible deliverables (Step 1 hero, Step 3 workspace).
- **D22. Install `react-force-graph-2d` and `react-force-graph-3d`, not the umbrella `react-force-graph`.** The umbrella depends on the AR and VR renderers (A-Frame plus three.js) whether or not they are used, against a Step 1 done-when of "stays smooth on a mid-range laptop".
- **D23. The lock set is snapshotted into the `generated_prompts` row.** Locks are promised in three sections of the brief and stored in none. Without a snapshot, Step 6's "tell the user if the diff touched something locked" has nothing to compare against once the agent finishes.

## Step 2 parser, from research measured against the real demo repo (2026-09-19)

An agent rebuilt the proposed design against `heon-1219/coding-interview-prep` and
measured it: 20/20 alias imports resolved, 30 certain call edges, 12 renders, and
"kv is called from 6 places" fires. These are the corrections it found.

- **D28. Pin `ts-morph@27.0.0`, not latest.** ts-morph **vendors** its own TypeScript rather than depending on one, so npm cannot warn about a mismatch. Verified: 27.0.0 carries TypeScript 5.9.2 against the repo's 5.9.3, and sampled `SyntaxKind` values agree across the two copies. A version carrying TypeScript 6 would give two copies with different `SyntaxKind` numbers, making kind-based dispatch fall through to no-op branches — a graph with whole node types missing and no error anywhere. Also corrected: ts-morph was never installed; an earlier note in this session reported a registry version as if it were an installed one.
- **D29. `allowJs: true` and `moduleResolution: Bundler` are the two options that decide whether the graph connects at all.** Measured: `allowJs: false` puts **0 of 17** demo files in the program **and reports zero diagnostics** — the run succeeds, D20 sweeps, and the previous graph is replaced with nothing. `Node16`/`NodeNext` resolve extensionless `./Button` to nothing, which is D15's failure arriving from a different direction. Never inherit the repo's `moduleResolution`.
- **D30. Rewrite `paths` substitutions to absolute before handing them to the compiler.** `paths` without `baseUrl`, passed programmatically, resolves against **our process working directory** and silently returns unresolved. The demo repo's jsconfig.json is exactly `{"compilerOptions":{"paths":{"@/*":["./*"]}}}` — no baseUrl. A rooted substitution makes the base irrelevant.
- **D31. Write every node first, then every edge.** Edges have foreign keys to nodes, and a `renders` edge is routinely emitted before its target file has been parsed. The brief's "loop each file, write nodes and edges" is therefore not implementable as written. Two passes.
- **D32. Drop any call edge whose source equals its target.** The nearest-enclosing-symbol attribution rule makes components call themselves: **133 self-loop call sites** on the demo repo, and the six highest-weight edges in the entire graph were self-loops.
- **D33. Guard the name-match fallback structurally, not by name.** An import from an uninstalled package returns the compiler's `unknown` symbol with zero declarations — indistinguishable from "resolution failed". The fallback then fabricates `inferred` edges from `useRouter` and `slugify` onto same-named local helpers. Capture `symbol.declarations[0]` **before** the alias loop; if it is an import or export specifier, emit `uses_package` and never consult the name index.
- **D34. Reject any resolution whose declarations span more than one source file.** A `.js` file with no import or export is a *script* in TypeScript, so its top-level functions merge into one global scope with every other script file. `init()` resolved to a symbol declared in two different files, and taking the first would emit a `certain` edge to a coin flip.
- **D35. Only emit an edge when the resolved declaration is one we actually created a node for.** A JSX tag bound to a destructured prop (`function Wrapper({As}) { return <As/> }`) resolves *successfully* to a BindingElement — it passes every "did the checker answer" test and yields an edge to a node that never existed, which is a foreign-key violation or a phantom node.
- **D36. Assert `filesParsed > 0` whenever ingest offered files, and skip D20's sweep when a run fails that assertion.** This is the tripwire for every silent-emptiness failure above.
- **D37. Carry a skipped file's previous rows forward by touching `last_seen_run_id` before sweeping.** Otherwise D20's sweep amplifies through `ON DELETE CASCADE`: one file becoming unparseable in run two deletes its nodes and takes every edge from *healthy* files with them.
- **D38. Detect an unparseable file with `getSyntacticDiagnostics`, not try/catch.** A merge-conflict file does not throw — the parser recovers and yields usable statements (measured: one surviving function declaration, three diagnostics of code 1185). A try/catch never fires, so the file would be silently half-analysed.
- **D39. Environment hazard, worth knowing before it wastes a day.** A stray `node_modules` directory sits above the system temp directory on the founder's machine, so `react` and `@types/react` resolve locally and will not on Railway — 223 call sites classified differently and a fivefold slowdown. The graph came out identical only because of the declaration-file exclusion and D33's guard; remove either and development and production diverge silently.
- **D40. The id separator is now written as an escape sequence.** `src/analysis/ids.ts` contained a **raw NUL byte** in its source, which made the file read as binary to grep and diff. It was functionally correct — the space-collision test passes against the real module, so the reported collision did not reproduce — but a literal control byte in source is exactly what gets mangled in transit, and if it ever were, `assets/me sitting 3.jpg` in the founder's own portfolio is a real colliding path.

## Step 2 parser, as built and measured (2026-09-19)

- **D41. An import is a package when it resolves OUTSIDE the repository, not when it fails to resolve.** D39 predicted this and it happened on the first live run: a stray `node_modules` above the system temp directory makes `react` resolve to a real file on the founder's machine, so it was treated as an in-repo import and then dropped for pointing outside the repo — while on the server, with no such directory, the same import resolves to nothing and correctly becomes a package. `react` was silently missing from the graph on one machine and present on the other. Deciding on repository membership rather than on resolution success makes both environments agree.
- **D42. Node and edge identity keys are JSON, not delimiter-joined strings.** Any separator must be a character that cannot occur in a path or a name, which in practice means a control character — and a literal control character in source is exactly what gets rewritten in transit. This codebase has now had the same escape become a raw NUL byte in one file and a plain space in another. Either would make `assets/me sitting 3.jpg` collide with a different node, silently overwriting one and repointing its edges. JSON encodes the boundary structurally. The persisted hash was changed to match while no graph existed to migrate.

## LLM provider (2026-09-19)

- **D43. There are two separate LLM configurations in this product, and they are not interchangeable.**
  - **Ours** (Step 4): Pass 2's semantic layer and the Q&A agent. Our server calls it, we pay for it, and it is configured by `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`.
  - **OpenCode's** (Step 6 stretch only): the user's coding agent running inside the sandbox. Verified: **OpenCode does not read our three env vars.** It requires its own `opencode.json` with a provider block (`@ai-sdk/openai-compatible`, its own baseURL and key). So even in Step 6 these stay two configurations.
  - For the MVP, OpenCode is not in play at all: the deliverable is a prompt the user pastes into whatever agent they already use. So "users can pick any model in OpenCode" is true, and it does not answer what powers our Q&A.
- **D44. Pin a single serving endpoint. Do not point `LLM_BASE_URL` at a router.** MiMo-V2.5's capabilities differ **by serving provider, not by model**, and the differences are exactly the ones we depend on. Per OpenRouter's own endpoint listing: GMICloud (cheapest) supports `tools` but not `response_format`; **StreamLake supports `response_format` but not `tools`**; Xiaomi's own endpoint supports both; DeepInfra and Venice support everything. OpenRouter routes by price and latency, so **the same key can land on a tool-less provider between runs** — the Q&A agent would work one day and silently fail the next, which is the worst failure shape this product has. Recommended: `LLM_BASE_URL=https://api.xiaomimimo.com/v1`, `LLM_MODEL=mimo-v2.5`.
- **D45. `mimo-v2.5` and `mimo-v2.5-pro` are different models released the same day, and the brief names the wrong one for this job.** `MiMo-V2.5` (310B total / 15B active) is the **omnimodal** model — its tags are multimodal, vision-language, audio, video. `MiMo-V2.5-Pro` (1.02T / 42B) is the one tagged `code` and `agent`, positioned by Xiaomi for software engineering. We use no images, audio or video whatsoever. Cost differs roughly tenfold (~$0.14/$0.28 vs ~$1/$3 per M tokens). Keep `mimo-v2.5` as the default since it is cheap and does tool calling, but provision Pro on the same key so Step 4 can A/B feature naming on the real demo repo and choose on evidence. Env-only configuration makes that a one-string change.
- **D46. Never put node id hashes in an LLM prompt.** The binding constraint in Pass 2 is the **output** budget, not the input: a ~300-file app outlines to 45–90k tokens, comfortably inside a 1M window, but echoing ~2,400 hex ids back costs 20–25k output tokens against `mimo-v2.5`'s 32,768 default completion limit, competing with reasoning tokens. Number the nodes sequentially in the outline (`[147] PayButton (component) app/checkout/PayButton.tsx`), ask for integer indices, and map back to hashes in code. Cuts id cost about fivefold on both sides and turns section 6.2's "drop any id that doesn't exist" validation into a bounds check.
- **D47. `supportsStructuredOutputs` defaults to false, with Zod validating the parsed result.** It is a per-endpoint fact that cannot be derived from the base URL, and setting it true against an endpoint that does not advertise `json_schema` produces either a 400 or a silently ignored constraint. Section 8 already requires treating LLM output as untrusted, so validation is not extra work. A fourth optional variable, `LLM_SUPPORTS_JSON_SCHEMA`, keeps switching endpoints a config change rather than a code change.
- **D48. The AI SDK's current major is 7.x and its API moved substantially.** `generateObject`/`streamObject` are gone, `stepCountIs` became `isStepCount`, `system` became `instructions`, and the SDK is ESM-only on Node 22+. Any tool-loop or structured-output code written from older knowledge will not compile — check the current docs when Step 4 starts rather than trusting a remembered signature.

## OpenCode and token cost, settled (2026-09-19)

David asked for two things at once: route all our LLM use through OpenCode, and
reduce token input/output. Researched at source level. They turned out not to be
in tension — one research agent claimed OpenCode's tool definitions could not be
removed, and the critic read the source and refuted it: `permission: "deny"` does
strip them, leaving about 100 tokens per step rather than 5,144. So tokens did not
decide this. Something else did.

- **D49. OpenCode owns Step 6 only. Pass 2, the Q&A agent and 6.4's restatement stay on direct AI SDK calls — and the reason is trust, not tokens.** `session/prompt.ts` unconditionally promotes the analysed repository's own `AGENTS.md` into OpenCode's system prompt. That is fine for a coding agent working on those files, and it is not fine for Pass 2, because Pass 2 is the pass that **names the features a non-developer will read as fact**. A file inside the repository we are analysing would be able to influence what we tell the user their own app contains. The split is therefore the same line as the trust boundary: OpenCode handles anything touching the **user's files**, direct SDK calls handle anything touching **only our graph**.
- **D50. One source of truth for the model, which is what David actually wanted.** `src/lib/llm/config.ts` exports `{ baseURL, apiKey, model, supportsJsonSchema }` from the four env vars. Our three call sites import it, and a small serializer emits the same values into `OPENCODE_CONFIG_CONTENT` for the Step 6 sandbox. **One env var changes the model everywhere**, with no agent loop in the inference path. D43's two clients remain; the configuration is no longer duplicated.
- **D51. Custom tools through OpenCode do work, for the record.** Two mechanisms exist — a file-based `.opencode/tool/*.ts` plugin, and a remote MCP server configured inline via `OPENCODE_CONFIG_CONTENT`. The output ceiling is computed from the batch, not chosen once — and the defect that forced it is the kind this repository only finds by measuring.** The first version sent a flat 2,000 tokens per naming call. The first batch of the first real run carried 20 files and 120 pieces, answered at **1,985 tokens with `finishReason: "length"`, and was discarded whole**. The run completed, the coverage event reported full coverage, and **every Python source file in the project came back unnamed while its markdown was named perfectly** — a map with no words on exactly the half that matters, and nothing anywhere reporting it. Nothing in the code looked wrong; the number did. The ceiling is now `240 + 70·files + 30·pieces`, from the measured 51–53 output tokens per file, and a truncated reply is counted as a `truncated` drop and re-asked once **without its pieces** rather than lost. After the fix: no truncation, and names went from **34 of 202 to 114 of 202** on the same project.
- **D89. A feature's `name` is a hash of its members; a feature that keeps its Korean name or most of its members keeps its id.** D55 required that a rename must not change a feature node's id, because the id is a hash of `name` and D20's sweep plus `ON DELETE CASCADE` would then silently delete the user's own `belongs_to` corrections. Every readable structural key was worse: the members' common directory collides (on a normal app 결제 and 장바구니 both reduce to `src`) and the top-ranked member's path churns with degree. So the key is `feature:` plus 12 hex of SHA-256 over the sorted member paths — never shown, since `grouping.ts` draws `label ?? name` and this pass always writes a label. A hash of members is stable under a rename and unstable under a membership change, which is the opposite half of the same problem, so a feature first inherits the key of a previous feature with **the same Korean name**, then of one sharing **half its members**. Observed on the real project: the model renamed 매매 전략 to 투자 전략 between two runs and the node kept id `feature:17ce8de2ac7a`.
- **D90. A run with no model, a failed model call or a truncated feature reply restates last run's features rather than losing them — and that is a correctness requirement, not an optimisation.** A `feature` node has no `file_path`, so `carryForwardSkipped` (which finds rows by path) cannot stamp it, and the sweep deletes every row a successful run did not see. Without the restatement, one run with a missing API key would delete every territory on the map and cascade every `belongs_to` pointing at it, including the user's. Conversely a `belongs_to` from an *unchanged* file is stamped by the `outgoing` carry-forward rule whether or not this run still believes it, which would leave a file in its old feature and its new one at once — so Pass 2 sweeps its own `belongs_to` rows against its own run id before the general sweep. Measured: 10 stale links removed on the second real run.
- **D91. The pipeline owns the run's phase; an analyzer only knows when its own half is finished.** Every analyzer ends with `emit.phase("done")`, which was true while Pass 1 was the whole run and became false the moment Pass 2 landed — the checklist would reach 다 됐어요 and then go back to 기능 이름 붙이는 중, which reads as the analysis restarting. The emitter swallows `done` from an analyzer and the pipeline emits it after Pass 2, rather than editing the three analyzers that are each right about themselves. Verified on the event stream: `ingest → static → semantic → semantic → feature.created ×6 → node.assigned → done → run.completed`.
- **D92. A re-read of a repository nobody pushed to costs zero model calls, by not asking rather than by copying.** `persist.ts` deliberately leaves `label`, `summary` and `text_lang` out of Pass 1's upsert, so an unchanged file's Korean survives a full re-write of its row; carrying forward is therefore the *absence* of work. Pass 2 skips any file that already carries Korean text and is not in the incremental change set, and skips the feature call entirely when nothing was asked. **Measured on the same project: 0 calls, 0 tokens, 48 names carried forward.** Deliberately keyed on "nothing was asked" rather than "nothing came back named", so a batch whose answers were all rejected cannot be misread as a project that did not change.
- **D93. `ANALYZER_VERSION` 2 → 3.** A carried-forward row from a version-2 graph means something different now: version 2 had no `feature` nodes, no `belongs_to` edges and no plain-language text on anything. One full write per project, then incremental again.
- **D94. The 기능 grouping is now reachable on a real project, and `grouping.ts` turned it on with no code change, exactly as its header promised.** Measured on `Kim-and-Chang-` after Pass 2: 219 items, 6 territories of 46 / 45 / 36 / 30 / 10 / 6, residue 40 (18%, against the 50% limit), largest share 21% (against 85%). The model deliberately leaves documentation and configuration ungrouped — the prompt tells it to rather than forcing a home — and D52's inheritance through `contains` is what turns 19 assigned files into 179 placed items.
- **D95. The Korean filters earn their place on real output.** `안전`, `노드` and `엣지` are rejected in a model's label and summary the same way they are in `qa/answer.ts`, and a summary must end in 요 or it is dropped rather than rewritten. On the first real run of a repository containing `safety.py` the forbidden-word filter fired **once**, which is the whole argument for having it: the model reached for 안전, and the one word this product may never say about somebody's code did not reach them.

## The workspace on a phone (2026-09-21)

- **D96. One layout that changes shape, not a second codebase — and the shape below `md` is one pane at a time.** The founder's report was "모바일에서 UI 깨지는 부분들이 있어(로그인 후 레포지토리 선택 등)" and the proposal was a separate mobile build. Two codebases means every bug twice, so this is one tree that changes shape at 768px (Tailwind's `md`, written as `max-md:` in CSS and `(max-width: 767.98px)` in `panes.tsx` — the fraction matters, because `767px` leaves a sliver at 125% zoom where neither query matches). Above the breakpoint nothing changed: measured at 1280px, the columns are still 215.9 / 5 / 736.6 / 5 / 317.5px and the phone row is `display: none`.
- **D97. The mechanism was already in the file: `PaneChips`.** It maximised a pane; on a phone it *is* the navigation — `role="tablist"`, one of 지도 / 파일 / 연결 / 변경 기록 always selected, roving tabindex, 44px targets, and pressing the lit one does nothing rather than returning to a layout this width cannot draw. The pane it selects is a **separate** value from `maximized`, and that separation is the bug it avoids: reusing `maximized` would mean a phone never has it null again, so rotating a tablet back to a wide layout would show a workspace with two of its three columns collapsed and no memory of anyone asking for that.
- **D98. Switching panes is not a remount, and that is the load-bearing constraint.** UI_DIRECTION §5.2: a React component that changes parent loses its IME composition, so a half-typed 한글 syllable in the 연결 pane's request box disappears. The phone layout is therefore the same JSX with a different grid template — the three panes you are not looking at are at zero width, `inert`, and still mounted. Verified in the browser: a textarea marked with a JS property kept the property, its text (회원가입은 어디서) and the panel's 90px scroll offset across three pane switches **and** across a resize from 375 to 1280 and back.
- **D99. Both templates travel as custom properties and CSS picks one; JavaScript never decides the width.** An inline `grid-template-columns` beats every class, so a media query could not have the last word over it — and it would also be the server's guess about a width the server does not have, which is one frame of the three-column layout on every phone that opens the page. So `--pane-cols` / `--pane-cols-phone` are set in `style` and `[grid-template-columns:var(--pane-cols)] max-md:[grid-template-columns:var(--pane-cols-phone)]` chooses. `usePhoneLayout()` still exists, over `matchMedia` through `useSyncExternalStore` like the rest of the module, but only for `inert` and for taking collapsed dividers out of the tab order — things a one-frame flash cannot be seen in.
- **D100. The workspace's overflow was the dashboard's bug again, one level down: a grid item's `min-width: auto`.** The panes are wrapped in `min-w-0` grid items, but the `<nav>` and `<aside>` *inside* those wrappers were grid items themselves with the default `min-width: auto`, so they could not shrink below their content: measured at 375px, a 0px column holding a 275px panel. `min-w-0` on both roots is the whole fix, and it is the same sentence as `grid-cols-1` in `41eb8e5` — **a track or an item that has not been told it may be narrower than its contents will not be.** Third time; it is worth reading the wrappers before anything else next time a pane spills.
- **D101. Measuring "past the right edge" needs three numbers, not one, and D72's instruction has an edge.** Lifting *every* `overflow-x` guard (D72) also lifts the ones that are the mechanism rather than a guard: a `truncate` ellipsis, a horizontal code scroller, the map's 1px-wide screen-reader mirror, and the parked panes themselves. So the probe reports (a) raw rects past the viewport with all guards lifted, (b) the same excluding subtrees that are deliberately 1px or scrollable, and (c) **content clipped out of reach** — cut off inside a non-scrollable, non-ellipsis box, which is the exact signature of the dashboard bug and the only one of the three that was non-zero before this pass. Workspace at 375px: (c) went 79 → 0; at 320px, 85 → 0; at 414px, 46 → 0.
- **D102. Below `lg` the dashboard stops being a screen and becomes a page.** The two-column rule — viewport height, only the list scrolls — is right when there are two columns to keep in view and is the founder's reported bug when there is one: the picker and the project list each got half a phone, so "로그인 후 레포지토리 선택" was a search field over a 110px window onto a list of repositories. One column, content height, one scroll, and the repository list capped at `60svh` (`svh` rather than `vh`, because on a phone `vh` is the *tall* viewport and a `vh` cap is taller than the screen whenever the browser's own bar is showing). Seven repositories visible at 375px, against two.
- **D103. `group-hover` is the one reveal with no touch equivalent.** The 열기 button on every row of the file list was `opacity-0 group-hover:opacity-100`, which on a phone is a control that never appears — and it is the only way to open a file from that list. It is simply present below `md`, where the column is the whole width and the room it was hiding to save is room that exists.

## Performance, measured before it was touched (2026-09-21)

- **D104. The answer stream had no heartbeat, and that is a fault Railway kills in production.** `events/route.ts` was written against D17 and carries all three of its requirements; `ask/route.ts` was written later, spelt its own headers by hand and sent **nothing at all between frames**. Railway closes a request after five minutes with no data transferred, and the investigation loop is silent for exactly as long as the model thinks — so a `deep` question on a large project could have its connection closed under an answer that was on its way, and the person would see the steps stop and a "연결이 끊겼어요". The transport is now `src/lib/ask/stream.ts`: `SSE_HEADERS`, `toSseFrame` and `heartbeatFrame` from `@/analysis/events` (one description of an SSE frame, not two) plus the pump those three do not include — a keepalive before the run starts, then one every 20s of silence, reset by any real frame, cleared in a `finally` and on abort. **The brief for this work said `no-transform` was missing too; it was not** — it was already there, and saying so matters more than looking thorough.
  - **The headers are strengthened, not replaced.** `Cache-Control` keeps `no-cache, no-transform` from the shared value and adds `no-store, private, must-revalidate`. The analysis stream carries counts; this one carries one person's question and quotations from one person's source, and nothing between them and us may hold a copy. Everything else is spread from `SSE_HEADERS` so a second spelling of `X-Accel-Buffering` cannot drift.
  - **A separate module because the route cannot be imported by a test.** It reaches `@/db`, `@/qa` and `@/lib/llm`, all of which sit on `@/lib/env` — 21 variables validated at import time, and a throw if one is missing. `stream.test.ts` imports one dependency-free module instead, and was verified by breaking it: deleting the heartbeat and weakening `Cache-Control` fails two tests; restoring them passes ten. **No millisecond budget is asserted** — the heartbeat test drives the clock by reading until the keepalives it wants have arrived, so a machine running four agents' builds cannot flake it.

- **D105. The event stream polled a database in Singapore 84% of the time for nothing, and now backs off.** Measured over the nine real runs in the database: at the fixed 400ms interval those runs would issue **910 queries, 764 of them returning no rows**, because a run is bursts separated by silence and the longest gap between two events is **43 seconds** — Pass 2's model call, which emits nothing while it thinks. The poll now grows ×1.5 per empty read to a **1600ms** ceiling and snaps back to 400ms the instant a row arrives. Replayed against those same nine runs: **910 → 363 queries, 60% fewer**, and the price is the single worst-placed event appearing **0.85s later**, mean **+0.14s**. That price is only ever paid at the end of a long silence — on a screen that has not changed for tens of seconds — and never during the file-by-file burst, which is the part somebody actually watches move. A 3000ms ceiling was measured too and rejected: 70% fewer queries but **2.2s**, which is long enough to read as a stall.

- **D106. The session is read once per request instead of three times.** Opening one project asked for the same row three times — `app/layout.tsx`, `generateMetadata`, and `ProjectPage` — all inside one request. Better Auth's `findSession` is one `session JOIN user` round trip each (verified in its own source; it joins rather than issuing two queries), so that was **three identical queries to Singapore for a row that cannot have changed between them**. `getSession` is now wrapped in React's `cache`. Per workspace page load: **8 database queries → 6**. Per dashboard load: **4 → 3**. Measured from this machine, one round trip to Neon is **75ms** (`/api/health`, which is exactly one `select 1`, answers in 76.9ms against 5.2ms for a static page); on Railway in the same region it is single-digit milliseconds, which is the honest way to state the size of this.
  - **Per request, and only per request.** The memo lives in the cache map React creates for the request being rendered. It is not a store, it has no TTL, and the function takes no arguments so there is no key to get wrong. Outside a React request scope `cache` calls straight through — verified in the installed React source — so this is a saving where it applies and today's behaviour where it does not, never a different answer. A session cache that crossed requests would hand one user another user's account, which is the worst failure this codebase has; that is why the mechanism is React's per-request one and not a module-level map.

- **D107. Four things that looked worth optimising, measured, and left alone.** Each of these is the kind of change that reads as obviously good and is worth nothing, and the number is the only thing that says so.
  - **No new index.** Every query in the product is already on the right index or correctly on a sequential scan of a tiny table; server-side `Execution Time` is **0.04ms–1.32ms** everywhere, including `loadGraph`'s two big reads. Tested at **400× today's data** on temp tables (480,000 nodes, 840,000 edges): the existing `nodes_project_path_idx` and `edges_project_source_idx` give **1.56ms and 1.70ms**. Adding the perfect ordering indexes — `(project_id, file_path, start_line, name)` and `(project_id, id)` — gives 0.64ms and 1.03ms, **saving 1.6ms for 94 MB of index on 288 MB of table**. Not worth a migration now and not worth one at four hundred times this size.
  - **Nulls in the graph payload cost nothing.** Dropping `label`/`summary` when null saves 30.7KB of JSON and **0.5KB gzipped — 0.3%**. `shape`, `fromUser` and the zero `uses`/`usedBy` counts together save another 0.4%. gzip eats repeated keys, which is the whole point: the obvious tidy-up is measured in bytes nobody pays.
  - **`WRITE_CHUNK = 500` stays.** On the largest real project (1,121 nodes, 2,123 edges) it is **8 round trips**; raising it to 2,000 makes it 3, at 18,000 bound parameters and a 508KB statement. Five round trips saved against a run that takes **66 seconds** is a rounding error, and the smaller statement is the one that can be read in a slow-query log.
  - **Compression is already on.** Railway's edge returns `content-encoding: gzip` and `next start` does too, so the graph payload is compressed on the wire without anything being added. `Cache-Control: private, no-store` does not prevent it; `no-transform` would, which is why only the two SSE routes carry that.

- **D108. The graph endpoint sends 62KB of compressed hash that the browser throws away — and the fix is in a file this work does not own.** Measured on `vestra-code`'s own map, 1,495 items and 3,030 connections: the `GraphView` is **855.0KB of JSON, 201.2KB gzipped**, and `connections[].id` — a 32-character hash, one per edge — is **118.4KB of that JSON and 62.2KB of the gzip, 31% of the entire compressed payload**. Keeping the field but making it the connection's array index instead of the hash recovers 51.7KB (25.7%); removing it recovers all 62.2KB, and is the smaller diff. `scene.ts` builds its drawable links from `from`, `to`, `relation` and `certainty` and never reads `id`; the walk overlay matches on `hop.from`/`hop.to`. The only reader is `src/qa/trail.ts`, which is server-side and holds the view in memory. So a third of what every user downloads before the map appears is a key nothing on that side of the wire opens. The change belongs in `view.ts` and `load.ts`, which another agent is editing this wave, and it is in the report rather than in this commit.

## The investigation goes rummaging (2026-09-21)

The founder's ask, verbatim: "AI가 조금 더 프로젝트 뜯어보는 과정에 참여해도 좋을 것 같아. 파일들 뒤져보았으면 좋겠어." The loop already existed and already worked; it was too timid, and every number below came off running it against a real project rather than off an argument about it.

- **D109. The loop can look inside files, not only at their names.** `find_items` runs the map's own beam over names, labels and paths — right for "where is PayButton", useless for the founder's own example, "결제가 어디서 이뤄져요", on a project whose word for it is `stripe`. `search_source` matches the bytes instead: a case-insensitive substring, **never a regular expression**, because a pattern written by a model is a pattern nobody reviewed running over somebody's own files, and the cheap version of that mistake is a catastrophic backtrack that spends the whole wall-clock budget on one file. Bounded four ways, each bound said out loud in the result: **60 files looked inside**, **1 MB pulled**, **10 matches shown**, **3 per file** so one generated file with four hundred hits cannot crowd out the nine that matched once each — which is exactly the case where the answer is in one of the nine. The coverage sentence always names both numbers ("프로젝트 파일 200개 중 60개를 들여다봤어요"), because "I searched the project" and "I searched sixty of its two hundred files" are different statements about somebody's code.
- **D110. A match registers its own line as read, and nothing around it.** The ledger entry is `{path, n, n, read: true}` — the bytes of that line came back, so a claim about that line may be `certain`; a claim about the six lines around it is refused as `unread_citation`, because `coverageOf` demands containment and the narrower claim is always available. The rule the product rests on is about **the bytes, not about which tool fetched them**, and `types.ts` now says so: `read_source`, `read_file`, a `search_source` hit and the head `follow_import` opens all make a line citable; a line range the *graph* merely told us about still does not. Each of the four has a test that builds a finding on its ledger and checks it survives, and a companion that checks a wider claim on the same ledger is refused.
- **D111. Three more ways to move, each one step where it used to be three.** `list_tree` — folders with the count of **everything beneath them**, three levels, forty rows; `src/` reporting 3 because three files sit at its root while 211 more sit two levels down is the number that sends a loop into the wrong folder. `read_file` — a whole file up to 160 lines and 6,000 characters, at most a fifth more than one `read_source` window and one fewer round trip to the same bytes. `follow_import` — resolve the name on an import line to the file it means and open its first 40 lines, crossing a connection the graph already holds so `trail.ts` draws an edge by its own id rather than one we invented. Two traps in that last one, both found by a failing test: **a dot means an extension in `base.py` and a module separator in `strategies.base`**, and treating them alike turns every Python import into a lookup for a file called `strategies` — so a trailing segment is an extension only when it is one, from a list. And the tool must report the file it **stood on** as well as the one it landed on, or the trail drops the hop for having only one end on the walk and redraws a real traversal as a coincidence.
- **D112. A search that could not open a file never reports an absence.** Found by running it: with GitHub rate limiting every read, `search_source` returned `"stop_loss"를 파일 48개에서 찾아봤는데 없었어요` about a project that contains it. The model believed it, and so would the person reading the trace — a false claim about somebody's own code, which is the most serious kind of defect this product can ship. Files opened and files refused are now counted apart; **zero opened is a refusal that says we could not look**, and "없었어요" is bounded to "들여다본 파일에는" even when some did open. A tool may say what it saw. It may never turn what it could not see into an absence.
- **D113. Rate limiting is its own refusal reason, and the loop is told once rather than seven times.** `readers.ts` folded GitHub's 403/429 in with every other failure as `unavailable`, and a loop that cannot tell them apart keeps trying: measured, **seven of twenty steps** went on opening seven different files and being told the same thing about each, and the investigation then answered `inferred` on a project whose source had been perfectly readable ten minutes earlier. `SourceRefusal` gains `rate_limited` with its own sentence, and after **three repository-wide refusals in a row** the tool result says plainly that opening files is not working and to answer from the map. A deleted file and a binary do not count toward that run — those are facts about one path — and the run resets the moment a file opens, because a blip is not an outage and a loop told to give up on a working repository would answer `inferred` for no reason.
- **D114. A content search holds what it scanned for the rest of the question.** Two searches over a 48-file project is 96 requests against an unauthenticated limit of 60 an hour, and the whole rest of that investigation then reads nothing at all. `ToolContext.held` keeps scanned text — **including refusals**, so a rate limiter is not asked twice — bounded at 1.5 MB and 200 files, written nowhere, gone with the request. Deliberately apart from the eight-file read cache: pushing a sixty-file sweep through an LRU built for the handful of files the loop is actually working with evicts the very window the model just asked about. The first search pays for the project, every later one is free, and a `read_source` after a search is free too. This does not change D77 — a GitHub project's source is still stored nowhere, and the ceiling here is inside what the read cache could already reach on its own.
- **D115. The budget is 20 steps / 150k input / 30k output / 180 seconds, and every one of those came off a measurement instead of an argument.** The old numbers were reasoned in prose: twelve steps because "twelve is the number a person waits through", 60k input from an estimate of the triangular history cost, 90 seconds because twelve round trips "is already a minute or two". All three were wrong in the same direction. Measured on the founder's real Python project (48 files, 213 pieces, 284 connections) with three questions a person would type: **all three used 11 of 12 steps**, one stopped at `tokens_spent` on step 11 having read 557 lines and filed **nothing**, and wall clock was **23–27 seconds against a ninety-second ceiling** — so the constraint everyone assumed was patience was in fact steps and tokens, and time was not close to binding. Input is linear at 4–6k a step once `HISTORY_FULL_STEPS` collapses older results, so twenty reading steps is about 120k and 150k keeps the token ceiling from being what stops a run; the **step** ceiling should be, because it is the one a person can feel. Output is a guard rather than a budget — measured at about eighty tokens a step, and `PER_CALL_OUTPUT_TOKENS` is what actually stops a runaway turn. 180 seconds sits inside D17 and inside the `/ask` heartbeat that landed the same day. **More budget buys more looking and never more confidence**: nothing in `answer.ts` loosened to pay for it, and "I ran out of steps having checked these three places" still has the same shape it had. `src/qa/measure.test.ts` is the harness, kept so the next person to move these numbers has to produce numbers too.
- **D116. The digest names where to start, and a place it names has to exist on the map.** A digest is a description and never evidence; that does not move, and nothing here touches the citation ledger. What changed is that it is now good at the one job it has. The build prompt asks for the file a document names, beside the word it names it for, and `placesIn` pulls path-shaped tokens out of the digest and keeps only the ones the project's own map holds — the same authority `read_source` uses to decide what may be opened at all. A bare name resolves only when exactly one file could be meant, because a guess with a coin flip in it is not orientation. Without the check, a README still describing a deleted file costs a step to open and a step to recover from, which is strictly worse than saying nothing. The path existing is ours; what is written inside it is still the author's claim, so the line reads **문서가 가리키는 자리** and sits inside the fence with everything else they wrote.

## The map at the size production actually holds (2026-09-21)

The founder's ask, verbatim: "그래프 보여주는 탭 UI 도 개선(겹침 x, 요소 많은데 어떻게 너무 난잡하게 안보일지 등)". Two complaints — things overlap, and a map with a lot on it reads as a mess. Every number below was measured on a synthetic project built at the size of the one in production, **1,442 items**, against a renderer whose every threshold had been set on a demo of 68.

- **D117. A renderer this size cannot be judged by looking at it, so it gets an instrument.** `render/probe.ts` records a real `drawMap` call against a counting stand-in and answers four questions with numbers: pairs of words lying on each other, words lying on a dot, dots lying on each other, and lines crossing lines. `scale-fixture.ts` builds the graph to measure it on — a realistic folder tree (two districts holding half the project, a long tail holding the rest), a power-law degree distribution, and **Korean label lengths**, because the existing recorder answered six pixels per character whatever the character was and a Hangul syllable is twice a Latin lowercase letter. Measuring a Korean-first map with a Latin ruler halves every collision count, which is the difference between "this is crowded" and "this is fine". The instrument found four separate faults that looking had not, in a file that already carried a scar (`lod.ts`'s threshold of 6.81 against a ceiling of 6) proving that looking does not work here.
- **D118. Every item-on-item overlap on the map was `HUB_BOOST`, and none of it was the packing.** Measured at the resting zoom: **seven pairs of overlapping dots with hubs and zero without**, at 900px and at 1400px, identically. The packing is sound — zero overlapping pairs in world space, tightest pitch 15.26 against a largest radius of 9 — and the boost was being applied at *draw* time to a slot sized for the unboosted radius, so the busiest thing in a territory simply grew over its neighbour. `HUB_BOOST` and `HUB_MIN_MEMBERS` therefore moved into `layout.ts`, which now places the hub at the middle of its territory and starts the rest at the first sunflower slot that clears `ITEM_R_MAX × HUB_BOOST + ITEM_R_MAX + 1` **measured through the band squash**, because a neighbour directly above the hub is only 70% as far out as one beside it. The reference overview the founder sent is a large node with dozens of small ones around it; it now is one.
- **D119. Every density rule in the renderer was dividing by the wrong area, by a factor of 3.9.** `viewFraction` asks "how much of the map is on screen at this zoom" and answered it with the **bounding box**. The map is discs with gaps between them inside a rectangle: measured on the 1,442-item project, the box is 2.09 million world units² and the area the packing actually fills is 536,000. So every budget derived from it overshot by the same factor. `MapLayout` gained `itemArea`, summed from the packing's own footprint rather than measured from the placed items, and `LodInput.mapArea` became `LodInput.itemArea` so nobody can pass the wrong one by habit.
- **D120. `RANK_CEILING = 220` was the operative relation-label budget, not the documented 28. A second 6.81.** Its own comment called it "a cost guard, not a design rule… the budget above already holds the expected count near 28". It did not: `RELATION_BUDGET` only ever set a *zoom threshold*, that threshold was clamped to the reachable zoom on any real project, and what actually decided how many words appeared was 220 — **7.9× the number the file documents** — multiplied again by D119's area error. Measured: **786 relation words on screen against a budget of 28**, with the guard itself sitting at a ceiling of 9,791 against 1,814 links, where it could never fire at all. The replacement is an identity rather than a tuning: `ceilingFor(budget) = budget / viewFraction`, so the expected number on screen is the budget exactly, at every zoom, still read off the zoom alone and therefore still immune to the pan-flicker the file exists to prevent. Names got the same treatment (they had no ceiling whatsoever, and drew 139 against a budget of 36) and lines got one of their own.
- **D121. A label that has nowhere clear to sit is not drawn, and the map says how many.** There was no collision resolution of any kind: **up to 513 pairs of words lying on each other**, and 3 to 7 of those at the *resting* zoom, between the territory names on the one screen this product opens with. `render/labels.ts` offers every word a short fixed list of places — under its dot, above it, out to either side; the midpoint of its line, then a little either way along it — takes the first that is clear, and **drops it** otherwise. A label over another label is worse than no label: two Korean words on top of each other are one smear that says neither, and a blank space is at least honest. Placement runs in priority order before anything is painted, because a file name taking the square inch a walk's step 2 needed would be the map answering a question nobody asked. After: **zero label-on-label and zero label-on-dot at every viewport, zoom and camera measured.**
- **D122. Exactly two words on this map may overrule the field, and both are answers to a question just asked.** A walk's hop **number**, because a walk with step 2 missing is not a smaller picture but a wrong one — the reader counts 1, 3, 4 and concludes the map lost a step that was never there. And the name of the item under the pointer, because a map that declines to say what you are pointing at is not answering. Both are placed first and everything else avoids them, which is what keeps the exception from spreading.
- **D123. `NAME_MIN_PITCH = 52` was a Latin sentence in a Korean-first product.** Its own comment: "a name is drawn under its dot at 11px, so about 52px of pitch is where two neighbours' names stop touching." 결제 화면 is 47px; `orderSummaryCard-118.tsx` is over a hundred; the **median** name on a real 1,442-item project is roughly twice the constant standing in for it, so names were being let on at half the zoom they need, every time. `thresholdsFor` now takes `NameMetrics`, measured by the painter through the same `measureText` it lays the words out with, over a fixed sample in name-rank order so it stays deterministic. The median and not the widest: one outlier path should not hold every name back, and the field drops what does not fit and says so.
- **D124. At a deep zoom the thing to cut is not the count of lines, it is the lines with both ends off screen.** Two budgets and one geometric rule, each with its own measurement. `LINK_BUDGET = 120` came from the crossing count: 1,517 lines on a 375px screen crossed each other **44,064 times**, fifty-eight crossings on the average line, and crossings grow as the square of the count, so about 110 is where a line can be followed end to end; 120 also matches the reference picture's ratio of lines to items. But the budget alone left 490 lines across a zoomed-in window with **75 crossings each — worse per line than before any of this**, because a long line crosses the window far more often than a short one and the survivors were the longest on the map. A line arriving from nowhere and leaving for nowhere is not a connection anybody can read, so a line is drawn only when one of its ends is within 120px of the window, or when it is exempt: a walk's own hop, or a line touching the selection or the pointer. After, at the same zooms: **185 to 3,573 crossings, from 40,929 to 86,957.**
- **D125. The map now says what it is not showing.** `drawMap` returns a `FrameReport`, and the map prints one sentence from it: "선 N개와 이름 M개는 겹쳐 보여서 지금은 줄였어요. 더 크게 보면 다시 나와요." Both mechanisms above decline to draw things on purpose and both would be a quiet lie without it — a map that omits in silence tells someone their project has fewer connections than it has, which is the failure D68 and `describe.ts` are both written against. It is the same promise `neighbourhood.ts` keeps with "N개는 줄였어요", and it ends with the remedy because a count with no way to act on it is only alarming. Written into the DOM straight from the draw pass rather than through React state: the counts belong to a frame, frames happen under a dragging hand at sixty a second, and routing them through `setState` would put a render inside every one of them.
- **D126. `FLOW_TRACKING.md` §6 asks for a path-aware focus and `scene.ts` already has one.** `Trail` is an ordered list of `TrailStep`, `stepFor` matches a link on **direction as well as ends**, and `linkStrength` returns `DIM` for anything that is not a hop — so the A→B→C-with-a-shortcut-A→C case the spec names is already impossible to draw ambiguously. What this wave added is the other half: the hop's order number survives both new budgets by exemption (measured — all six hops of a walk carry their number at 375px, 900px and 1400px at the zoom where the whole 1,442-item map fits), and a `TrailStep` with `connected: false` draws no line and no number, which is what a route→file→symbol joint must become, because no edge in the graph has those two ends. One change for whoever builds the flow picture: **the gap `drawThread` cuts is no longer always at the midpoint.** It is cut at whatever fraction the label field gave the word, which `drawRelation` and `drawThread` now both take, because a word slid along its line to dodge another word would otherwise leave its gap behind.
- **D127. The density term in every zoom threshold computed a number and then returned the same constant, so it is gone.** Each threshold used to solve "how far in must you be before only `budget` of these are expected on screen" and start drawing there. Measured across every project shape to hand, it asked for **10.4 on the 68-item demo, 15.9 on a 300-item fixture and 9.7 on the 1,442-item production graph — and all three clamped to 4.5**, at all three viewport widths. That is the 6.81 fault in a milder dress: a rule whose output does not depend on its input. It also cost the demo its relation words, which used to arrive at 3.0 with the lines and were being held to 4.5 for a density the demo does not have. The budgets did not move; D120's rank ceilings spend them exactly, which is the same arithmetic solved for the unknown it can actually be solved for. What is left is two statements a ceiling cannot make: **words never appear before the line they sit on**, and **a name needs physical room beside its neighbour** — the measured pitch, which is about how wide this project's words are and not about how many there are. `scaleForBudget` was deleted rather than left exported and unused.
- **D128. A word on a line takes the quietest place the line can offer, and is drawn only if that place is quiet enough.** The gap `drawThread` cuts opens one line, its own, so any other line crossing there runs straight through the word. Both obvious rules were measured on the 1,442-item project and both are bad: **refusing every crossed spot took the relation words on screen to one**, at every zoom and viewport, so "관계까지 엣지에 보여줌으로써" would never have happened on a real repository; **accepting any spot** brought them back to eight-to-twenty-five but with about **seventeen other lines through each**. So the field counts rather than merely checks: of the stops that clear every *word* and every *dot* — which is never negotiable — the word takes the least-crossed, and is held back if even that one carries more than two. Measured after: **one to seven relation words on screen with zero to fourteen crossings between them**, and the demo unaffected at twenty-eight words. The words also gained the halo item names already carry, which is what makes two survivable.
- **D129. Everything left in this product that a thumb could miss was on this map, and there was no way to zoom one without buttons.** Handed over by the mobile wave with measurements. **The legend and the zoom controls overlapped by 45 × 28px at 375px** — the legend running 12→316 and the buttons 271→363, both absolutely positioned over the canvas with neither yielding: the founder's 겹침, on the screen with the least room to hide it. The bottom-left column now takes the width that is actually left rather than all of it, and the legend wraps inside it. **`묶는 기준` was 113×36 and the three zoom buttons were 28×28**, the last sub-44px targets anywhere in the product; `max-md:min-h-11` is how every other control here says it and is how these say it now. And **there was no pinch**: the canvas already sets `touch-none` and already receives both pointers, so what was missing was arithmetic — two fingers now set the zoom by the gap between them, anchored on the point between them exactly as the wheel anchors on the cursor, and moving both together pans. A second finger ends a pan rather than fighting it, and lifting one finger from a pinch does not become a pan or a selection. Not verified in a browser: the harness the mobile agent used records **zero** ResizeObserver callbacks, so the rotation path is untested rather than known good.
