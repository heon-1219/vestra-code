## Architecture

- **D26. Two layers of analysis: a universal shallow layer and per-language deep layers.** David's call, 2026-09-19, answering "isn't the logic similar for any code? I want it to work anywhere."
  - The **shallow layer** runs on any repository at all: file tree, imports read as text, dependency manifests across ecosystems, route conventions where they are detectable. Everything it produces is `inferred`. Its job is that the product never tells anyone their repository is unsupported.
  - The **deep layer** is one analyzer per language, and it is the only thing that produces `certain` edges, because resolving a call to its definition is irreducibly language-specific — the TypeScript compiler for TS/JS, an entirely different machine for Python, Java, Go or Rust.
  - Why this split rather than "universal everywhere": the headline promise, "changing this affects these four places", is only worth anything when the edge is `certain`. A map built only from inferred edges is a screen of dotted lines, and the honest answer it gives to "will this break something?" is "probably, we are not sure" — which is not an answer. Section 3 forbids us from claiming more, so shipping shallow-only would mean shipping a product that runs everywhere and answers nothing.
  - Everything above the analyzer is already language-agnostic and was built that way deliberately: the graph model, stable ids, re-analysis rules, the map, Q&A, and the prompt builder. Adding a language is writing one analyzer, not rebuilding the product (D7).
  - **Closed, 2026-09-19, by research: there is no such thing.** The one project that promised both language-agnostic resolution and no dependency install was GitHub's `stack-graphs`, and **GitHub archived it on 2025-09-09** (API reports `archived=true`; its final commit is the archive PR; the crate is frozen at 0.14.1 from 2024-12-13). It only ever covered four languages. Nothing replaced it. Every other route is either one indexer per language or requires a working build, which we refuse to run.
  - And the split is language semantics, not a tooling gap that someone will close. TypeScript and pyright are error-tolerant front ends: they resolve intra-project imports from source alone and mark the rest unknown. Go, Rust, Java and C++ type checkers need the resolved types of every import, so with no dependencies installed they produce **nothing**, not degraded output. Hold anyone who claims otherwise to this.
  - **SCIP is alive and is the right post-MVP shape, but not now.** It moved to independent governance on 2026-03-25 and there is now an official Node reader (`@scip-code/scip`, published 2026-09-03) — neither was true when the brief was written. The blocker is that SCIP has no call role and no JSX concept: its roles are Definition/Import/WriteAccess/ReadAccess/Generated/Test/ForwardDefinition. Reference-derived edges conflate a call, a type annotation, a re-export and reading a constant, so writing them into `calls` as `certain` would be a stronger claim than SCIP itself makes — the exact dishonesty D25 put a Postgres enum around. And `renders`, the demo's best moment, has no SCIP representation at all. Post-MVP it becomes a third analyzer behind the D7 seam, emitting `contains`/`imports`/`uses_package` as `certain` and references as `inferred`.
  - **D26 CORRECTION: the shallow layer is not all-inferred.** As originally written this undersold the fallback. A `contains` edge never crosses a file boundary — `def charge_card` at lines 40-58 of `billing.py` *is* a function of that name at those lines, which is a direct read. Likewise `<script src="./app.js">` and `<link href="./style.css">`, which the browser resolves by a fully specified rule with no configuration, and `uses_package` when a bare specifier appears verbatim in the manifest. Those are `certain`. What is `inferred` is everything that crosses a file boundary **by name** — `calls`, `renders`, `fetches` — and relative imports in languages whose resolution depends on configuration we do not have. The practical consequence matters: in a fallback repo the boxes and their contents are solid and only the lines between them are dotted, which is a materially different product from a screen of dotted lines.
  - **Shallow-layer scope for the MVP is half a day**: file tree, dependency manifests across ecosystems, literal-path imports, and a project kind that routes here instead of erroring. Tree-sitter symbol extraction (`web-tree-sitter`, no toolchain needed) is the right way to add real symbols to this layer later — a Step 5-or-later item, not Step 2.
  - **Language priority, evidenced: TS/JS alone covers roughly 85-90% of the repos this product will ever be pointed at.** Every mainstream AI app builder except Replit emits React plus TypeScript, and GitHub's Octoverse put TypeScript at number one in 2025 attributing it explicitly to AI-assisted coding. Order: TS/JS deep (in flight), static HTML/CSS/JS deep (D6), universal shallow for everything else, then Python — and Python is cheap when it comes, because pyright is itself a Node program and costs no extra runtime on the image.
  - **A larger completeness threat than language coverage**, worth its own look before widening anything: for Lovable and Base44 users, much of the app is not in the repository at all — the backend is Supabase or Lovable Cloud configuration and SQL, and Base44 runs on a proprietary runtime. We could support every language on earth and still show those users an incomplete map.

- **D27. `NodeRef` carries an optional `container`.** Found by the same research, in code written an hour earlier. The ref was `{type, filePath, name}`, so a file declaring `render()` on three classes hashed to **one** node and every edge that should have pointed at one of the three merged onto whichever was written last — silently, with no error, telling the user something false about their own code. The container is the enclosing symbol's name, deliberately not a line number or an index, because both churn when unrelated code moves and rule 1 of section 6.1 requires an id that survives edits elsewhere in the file.

## From the stack audit, 2026-09-18 (25 agents, verified against current docs)

These are corrections to how the brief says to build things. Each one was found by
reading current documentation, and the high-severity ones were re-checked by a second
agent trying to refute them. Full run: 53 findings, 8 high, 1 refuted.

- **D15. Pass 1 must read `tsconfig.json`/`jsconfig.json` for `baseUrl` and `paths` only — never the rest of the config.** The brief (6.2) says to build the ts-morph project without the repo's tsconfig. Taken literally that is a silent failure: `@/components/Button` is a bare specifier, so TypeScript walks `node_modules`, which does not exist in an unbuilt tarball, and resolves to nothing. Every alias import in an idiomatic Next.js app would produce no edge at all, and Pass 1 would emit a confident, disconnected graph. Keep the brief's intent (the repo's `target`/`lib`/`strict` never decide our parse) but lift the path mappings out, tolerating comments and trailing commas, and fall back to probing `@/* → src/*` then `./*`.
- **D16. Starting a run and streaming it are two endpoints, not one.** `POST /api/projects/:id/analyze` starts the run and returns an `analysis_run` id immediately; `GET .../runs/:runId/events` tails *persisted* events by cursor (`Last-Event-ID`) and closes on `run.completed`. The brief's sequence diagram runs the pipeline inside the SSE request, which cannot satisfy Step 3's "refresh mid-run without losing state" — a refresh opens a second, isolated request with no access to the first run's emitter. This keeps 6.2's "the pipeline knows nothing about HTTP" intact and is the same shape a background worker would need.
- **D17. Railway's real limits, since D3 picked it: 15 minutes maximum per HTTP request, closed after 5 minutes with no data transferred, websockets exempt.** So SSE must send a heartbeat every ~20s unconditionally — including across the long Pass 2 LLM call — and the route must set `Cache-Control: no-cache, no-transform` and `X-Accel-Buffering: no`. (For contrast, Vercel is 300s hard on Hobby and 800s max on Pro, which is what D3 avoided.)
- **D18. Strip the tarball's top-level directory at ingest.** GitHub archives extract to `{owner}-{repo}-{sha}/`, so the commit SHA would land inside every `file_path` and stable ids would change on every commit — breaking rule 1 of section 6.1 exactly where it matters. Store paths repo-relative and POSIX-separated, and assert in the Step 2 tests that no stored path contains the repo name or a SHA.
- **D19. `chat_messages` stores user turns, final assistant text, and citation node ids — never tool results or source snippets.** The obvious chat implementation persists tool output so the conversation survives a refresh, but `read_source` output *is* the user's source code, which would put it in Postgres and break the section 3 trust promise in the first feature that touches it. Re-fetch on render instead.
- **D20. Re-analysis stages rows under the new `analysis_run_id` and promotes atomically at the end.** The brief says re-analysis "replaces" static and llm rows, which read literally means mutating the live graph while the user is looking at it, and a run that fails halfway leaves a half-graph. Staging means a failed run drops its rows and the previous graph stands.
- **D21. `next/dynamic` with `ssr: false` is illegal in a Server Component.** Pages are Server Components by default, so the brief's graph-rendering note compiles only behind a thin `'use client'` wrapper module per graph. Ten-minute fix, an hour of confusion if undiscovered — and it lands on both of the most visible deliverables (Step 1 hero, Step 3 workspace).
- **D22. Install `react-force-graph-2d` and `react-force-graph-3d`, not the umbrella `react-force-graph`.** The umbrella depends on the AR and VR renderers (A-Frame plus three.js) whether or not they are used, against a Step 1 done-when of "stays smooth on a mid-range laptop".
- **D23. The lock set is snapshotted into the `generated_prompts` row.** Locks are promised in three sections of the brief and stored in none. Without a snapshot, Step 6's "tell the user if the diff touched something locked" has nothing to compare against once the agent finishes.

## Step 2 parser, from research measured against the real demo repo (2026-09-19)

An agent rebuilt the proposed design against `heon-1219/coding-interview-prep` and
measured it: 20/20 alias imports resolved, 30 certain call edges, 12 renders, and
"kv is called from 6 places" fires. These are the corrections it found.

- **D28. Pin `ts-morph@27.0.0`, not latest.** ts-morph **vendors** its own TypeScript rather than depending on one, so npm cannot warn about a mismatch. Verified: 27.0.0 carries TypeScript 5.9.2 against the repo's 5.9.3, and sampled `SyntaxKind` values agree across the two copies. A version carrying TypeScript 6 would give two copies with different `SyntaxKind` numbers, making kind-based dispatch fall through to no-op branches — a graph with whole node types missing and no error anywhere. Also corrected: ts-morph was never installed; an earlier note in this session reported a registry version as if it were an installed one.
- **D29. `allowJs: true` and `moduleResolution: Bundler` are the two options that decide whether the graph connects at all.** Measured: `allowJs: false` puts **0 of 17** demo files in the program **and reports zero diagnostics** — the run succeeds, D20 sweeps, and the previous graph is replaced with nothing. `Node16`/`NodeNext` resolve extensionless `./Button` to nothing, which is D15's failure arriving from a different direction. Never inherit the repo's `moduleResolution`.
- **D30. Rewrite `paths` substitutions to absolute before handing them to the compiler.** `paths` without `baseUrl`, passed programmatically, resolves against **our process working directory** and silently returns unresolved. The demo repo's jsconfig.json is exactly `{"compilerOptions":{"paths":{"@/*":["./*"]}}}` — no baseUrl. A rooted substitution makes the base irrelevant.
- **D31. Write every node first, then every edge.** Edges have foreign keys to nodes, and a `renders` edge is routinely emitted before its target file has been parsed. The brief's "loop each file, write nodes and edges" is therefore not implementable as written. Two passes.
- **D32. Drop any call edge whose source equals its target.** The nearest-enclosing-symbol attribution rule makes components call themselves: **133 self-loop call sites** on the demo repo, and the six highest-weight edges in the entire graph were self-loops.
- **D33. Guard the name-match fallback structurally, not by name.** An import from an uninstalled package returns the compiler's `unknown` symbol with zero declarations — indistinguishable from "resolution failed". The fallback then fabricates `inferred` edges from `useRouter` and `slugify` onto same-named local helpers. Capture `symbol.declarations[0]` **before** the alias loop; if it is an import or export specifier, emit `uses_package` and never consult the name index.
- **D34. Reject any resolution whose declarations span more than one source file.** A `.js` file with no import or export is a *script* in TypeScript, so its top-level functions merge into one global scope with every other script file. `init()` resolved to a symbol declared in two different files, and taking the first would emit a `certain` edge to a coin flip.
- **D35. Only emit an edge when the resolved declaration is one we actually created a node for.** A JSX tag bound to a destructured prop (`function Wrapper({As}) { return <As/> }`) resolves *successfully* to a BindingElement — it passes every "did the checker answer" test and yields an edge to a node that never existed, which is a foreign-key violation or a phantom node.
- **D36. Assert `filesParsed > 0` whenever ingest offered files, and skip D20's sweep when a run fails that assertion.** This is the tripwire for every silent-emptiness failure above.
- **D37. Carry a skipped file's previous rows forward by touching `last_seen_run_id` before sweeping.** Otherwise D20's sweep amplifies through `ON DELETE CASCADE`: one file becoming unparseable in run two deletes its nodes and takes every edge from *healthy* files with them.
- **D38. Detect an unparseable file with `getSyntacticDiagnostics`, not try/catch.** A merge-conflict file does not throw — the parser recovers and yields usable statements (measured: one surviving function declaration, three diagnostics of code 1185). A try/catch never fires, so the file would be silently half-analysed.
- **D39. Environment hazard, worth knowing before it wastes a day.** A stray `node_modules` directory sits above the system temp directory on the founder's machine, so `react` and `@types/react` resolve locally and will not on Railway — 223 call sites classified differently and a fivefold slowdown. The graph came out identical only because of the declaration-file exclusion and D33's guard; remove either and development and production diverge silently.
- **D40. The id separator is now written as an escape sequence.** `src/analysis/ids.ts` contained a **raw NUL byte** in its source, which made the file read as binary to grep and diff. It was functionally correct — the space-collision test passes against the real module, so the reported collision did not reproduce — but a literal control byte in source is exactly what gets mangled in transit, and if it ever were, `assets/me sitting 3.jpg` in the founder's own portfolio is a real colliding path.

## Step 2 parser, as built and measured (2026-09-19)

- **D41. An import is a package when it resolves OUTSIDE the repository, not when it fails to resolve.** D39 predicted this and it happened on the first live run: a stray `node_modules` above the system temp directory makes `react` resolve to a real file on the founder's machine, so it was treated as an in-repo import and then dropped for pointing outside the repo — while on the server, with no such directory, the same import resolves to nothing and correctly becomes a package. `react` was silently missing from the graph on one machine and present on the other. Deciding on repository membership rather than on resolution success makes both environments agree.
- **D42. Node and edge identity keys are JSON, not delimiter-joined strings.** Any separator must be a character that cannot occur in a path or a name, which in practice means a control character — and a literal control character in source is exactly what gets rewritten in transit. This codebase has now had the same escape become a raw NUL byte in one file and a plain space in another. Either would make `assets/me sitting 3.jpg` collide with a different node, silently overwriting one and repointing its edges. JSON encodes the boundary structurally. The persisted hash was changed to match while no graph existed to migrate.

## LLM provider (2026-09-19)

- **D43. There are two separate LLM configurations in this product, and they are not interchangeable.**
  - **Ours** (Step 4): Pass 2's semantic layer and the Q&A agent. Our server calls it, we pay for it, and it is configured by `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`.
  - **OpenCode's** (Step 6 stretch only): the user's coding agent running inside the sandbox. Verified: **OpenCode does not read our three env vars.** It requires its own `opencode.json` with a provider block (`@ai-sdk/openai-compatible`, its own baseURL and key). So even in Step 6 these stay two configurations.
  - For the MVP, OpenCode is not in play at all: the deliverable is a prompt the user pastes into whatever agent they already use. So "users can pick any model in OpenCode" is true, and it does not answer what powers our Q&A.
- **D44. Pin a single serving endpoint. Do not point `LLM_BASE_URL` at a router.** MiMo-V2.5's capabilities differ **by serving provider, not by model**, and the differences are exactly the ones we depend on. Per OpenRouter's own endpoint listing: GMICloud (cheapest) supports `tools` but not `response_format`; **StreamLake supports `response_format` but not `tools`**; Xiaomi's own endpoint supports both; DeepInfra and Venice support everything. OpenRouter routes by price and latency, so **the same key can land on a tool-less provider between runs** — the Q&A agent would work one day and silently fail the next, which is the worst failure shape this product has. Recommended: `LLM_BASE_URL=https://api.xiaomimimo.com/v1`, `LLM_MODEL=mimo-v2.5`.
- **D45. `mimo-v2.5` and `mimo-v2.5-pro` are different models released the same day, and the brief names the wrong one for this job.** `MiMo-V2.5` (310B total / 15B active) is the **omnimodal** model — its tags are multimodal, vision-language, audio, video. `MiMo-V2.5-Pro` (1.02T / 42B) is the one tagged `code` and `agent`, positioned by Xiaomi for software engineering. We use no images, audio or video whatsoever. Cost differs roughly tenfold (~$0.14/$0.28 vs ~$1/$3 per M tokens). Keep `mimo-v2.5` as the default since it is cheap and does tool calling, but provision Pro on the same key so Step 4 can A/B feature naming on the real demo repo and choose on evidence. Env-only configuration makes that a one-string change.
- **D46. Never put node id hashes in an LLM prompt.** The binding constraint in Pass 2 is the **output** budget, not the input: a ~300-file app outlines to 45–90k tokens, comfortably inside a 1M window, but echoing ~2,400 hex ids back costs 20–25k output tokens against `mimo-v2.5`'s 32,768 default completion limit, competing with reasoning tokens. Number the nodes sequentially in the outline (`[147] PayButton (component) app/checkout/PayButton.tsx`), ask for integer indices, and map back to hashes in code. Cuts id cost about fivefold on both sides and turns section 6.2's "drop any id that doesn't exist" validation into a bounds check.
- **D47. `supportsStructuredOutputs` defaults to false, with Zod validating the parsed result.** It is a per-endpoint fact that cannot be derived from the base URL, and setting it true against an endpoint that does not advertise `json_schema` produces either a 400 or a silently ignored constraint. Section 8 already requires treating LLM output as untrusted, so validation is not extra work. A fourth optional variable, `LLM_SUPPORTS_JSON_SCHEMA`, keeps switching endpoints a config change rather than a code change.
- **D48. The AI SDK's current major is 7.x and its API moved substantially.** `generateObject`/`streamObject` are gone, `stepCountIs` became `isStepCount`, `system` became `instructions`, and the SDK is ESM-only on Node 22+. Any tool-loop or structured-output code written from older knowledge will not compile — check the current docs when Step 4 starts rather than trusting a remembered signature.
